# Location permission fix — Ember 0.4.1

The 0.4.0 location request could stay in `asking` or `locating` indefinitely. It requested iOS-style authorization without starting a location service. [Native macOS prompts when a location service starts](https://developer.apple.com/documentation/bundleresources/choosing-the-location-services-authorization-to-request). It also called `NSApp.activate()` and immediately requested authorization, even though activation is asynchronous. [Apple documents that a When In Use request does nothing when the app is not currently in use](https://developer.apple.com/documentation/corelocation/cllocationmanager/requestwheninuseauthorization()). Both required purpose strings were present, but the signed app lacked `com.apple.security.personal-information.location`. [Apple requires location resource access for Hardened Runtime](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.personal-information.location). The installed app’s signature confirmed it was absent.

The regression loop injects a CLLocationManager that does not return authorization or a fix. `testMissingPermissionCallbackDoesNotSpinForever` failed against 0.4.0 behavior: `asking` was still set after the configured deadline. Log: `build/location-fix/red.log`. The exact underlying OS state on Cohen's failed attempt was not captured; foreground timing is an identified failure path, not a claim that every spinner has the same cause.

The location entitlement is now included without enabling App Sandbox. A regression test reads the actual app’s code-signing entitlements; it failed before the entitlement was added (`build/location-fix/entitlement-red.log`). The request now waits for foreground activation, then calls `requestLocation()` to trigger the native macOS permission prompt. A 20-second deadline cancels stalled requests and shows Retry/Settings with fallback sun times. Duplicate refreshes cannot restart an in-flight fetch or extend its deadline. Successful fixes cancel the timer, and refresh freshness is persisted only after success. Denial stops pending work and stays denied. Authorization itself remains the user's choice.

A new setup window requests location immediately after becoming visible, including setup replay. There is no location prompt on ordinary launches after setup completion. Startup registration remains a separate preference rather than a location permission.

`xcodebuild -scheme Ember -configuration Debug -destination 'platform=macOS,arch=arm64' -derivedDataPath build/dd test` passed **70 tests, zero failures**, including six location regressions: missing permission callback, foreground gating, missing-fix recovery and retry, successful-fix persistence, denial, and the signed location entitlement. Log: `build/location-fix/test.log`. This uses isolated UserDefaults and does not change the user's permissions or location.

Changed: `Ember/Ember.entitlements`, `Ember/LocationService.swift`, `Ember/SetupView.swift`, `Ember/PreferencesView.swift`, `EmberTests/LocationServiceTests.swift`, version configuration/generated project, packaging guard, website release metadata, README and this report. `EmberTests/ScheduleTests.swift` now isolates UserDefaults too; its scrub test previously depended on the installed app having completed onboarding. Unit tests simulate Core Location callbacks.

## Native release verification

- Installed at `/Applications/Ember.app`, replayed onboarding, and observed stalled-request recovery. System Settings showed Ember's location switch off while system Location Services was on. Enabled Ember's switch as Cohen requested; the setup view changed to **Location allowed**, confirming an actual fix arrived. No location coordinates were printed or included in this report.
- Completed the Customize path without changing the current schedule. Ember is enabled, wake 7 AM, bedtime 11 PM, Standard strength and Open at login retained. The first-run flag was restored by setup completion. Previous installed candidates are retained under ignored `build/install-backup-*` directories.
- A fresh undecided user's system permission dialog was not exercised because this Mac already had an Ember entry with its switch off. The native macOS service-start behavior follows Apple's documented API; an existing off/denied permission may require System Settings rather than a repeat dialog.
- `git diff --check`, packaging shell syntax, 70 tests and the signed installed app are verified. Other unrelated runtime/device limits from the UI validation report remain unchanged.
